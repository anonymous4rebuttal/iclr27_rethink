# Supplementary rebuttal figures

**Visual conventions.** Structure comparisons use slate gray for Original, teal for Expert, orange for FFN, and purple for Layer. In `resource_quality`, circles, squares, and triangles identify 10%, 30%, and 50% pruning, and a diamond identifies the original model. Legends define the line styles used for response groups and independent seeds. The temperature figure uses its own temperature color scale.

**Resource measurements across pruning ratios.** `runtime_sweep` compares total parameters, reference FLOPs reduction, and measured time per output token for Original and Expert, FFN, and Layer pruning at 10%, 30%, and 50%. Measurements use one H20 GPU, BF16, vLLM 0.25.1, tensor parallelism 1, 512 input tokens, exactly 128 generated tokens, and one request at a time. Lines show medians of five timed batches after two warmup batches; latency bands show the interquartile range. Reference FLOPs use architecture-based arithmetic accounting with one multiply-add counted as two FLOPs. GLM Layer 10% and 30% remove 5/47 and 14/47 layers, respectively.

**Reasoning coverage and resource use.** `resource_quality` places each configuration's observed reasoning coverage against total parameter count, reference request FLOPs, and measured throughput relative to its original model. Coverage retention is the unweighted mean of four taskwise ratios: pruned pass@K divided by original pass@K, with K = 2,048 for AIME 2026 and Minerva Math and K = 512 for HumanEval+ and LiveCodeBench-v6. Quality measurements use the paper's 8,192-token output limit. Runtime uses the separate, fixed-length 512-input/128-output workload above. The figure combines the existing quality sweep with the resource benchmark; it does not measure end-to-end reasoning latency. Rebuilt 10% and 30% models reuse historical pruning selections. GLM Layer 10% matches the five-layer removal used in the paper's rounded 11% configuration; GLM Layer 30% has no corresponding math/code quality record and is omitted from this combined plot. Its resource measurements remain in `runtime_sweep`.

**Output length, success, and truncation.** Each `length_MODEL_TASK` figure redraws the corresponding points from Figure 3 in aligned panels, with Expert, FFN, and Layer pruning in separate columns. The first row shows mean output length in tokens for all samples (solid lines, filled circles) and for untruncated samples (dashed lines, hollow circles); the second row shows pass@1 (solid lines, filled circles) and pass@512 (dashed lines, hollow circles); the third row shows the percentage of outputs reaching the 8,192-token limit. Untruncated means below the output limit, irrespective of answer correctness. All original model/task/structure points are retained. Curve positions use the paper's displayed pruning ratios, which may be rounded for discrete structures. All pass@k values are recomputed from per-problem integer success/sample counts; pass@512 is used on all four tasks without extrapolation. The separation of the two length curves should be read together with truncation and accuracy, as a task-dependent diagnostic rather than a universal pruning cutoff.

CSV files contain the numerical values plotted. All percentages are on a 0–100 scale unless explicitly described as ratios. The length CSV includes repeated original-model points because each structure has its own baseline curve.
